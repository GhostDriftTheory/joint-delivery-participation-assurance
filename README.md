# 共同配送・参加拡張アシュアランス

**既存の共同配送網に、次の荷主と、次の収益を。**

配車・運行システムを置き換えず、新規荷主の参加条件・承認・引渡しと採算を確かめる、操作可能な公開PoCです。

物流事業者が検討するのは、「積めるか」だけではなく「既存荷主の条件を守り、利益を残して受け入れられるか」。この違いを、同じ入力から再計算できる形で示します。

株式会社AIアシュアランスによる公開参照PoCです。既存の配車・運行システムを置き換えず、そこから得る追加参加案を検証する構成を、合成データで再現します。

対象は、固定1ルート、運送会社1社、既存荷主A・B社、新規候補C社またはD社。正常、条件不足、容量超過、既存荷主の条件違反、承認の撤回・失効、計画の改訂、引渡しの未確認、赤字など38ケースを収録しています。実在企業のデータ・契約・料金は使用していません。

**公開対象は、固定された合成シナリオの限定的な参照実装です。商用基盤の全実装は含みません。** 実運行や実システムへの接続、実測された利益・工数削減は示していません。

## 投資検討に向けて、まず見る4つのケース

画面の代表ケースボタンから切り替えられます。表示数値は、すべて合成条件からの計算です。

| ケース | 画面で確かめること | 事業上の問い |
|---|---|---|
| JD01 成立・黒字 | 既存2社＋C社の参加案。重量ベースの積載率70%→85%、追加貢献利益8,000円／運行という合成例 | 既存便に顧客と収益を追加できる条件は何か |
| JD02 黒字でも承認不足 | 採算はプラスでも、必要な承認がないためHOLD | 何を、誰が確認すれば次へ進めるか |
| JD16 既存荷主に遅延 | 容量に収まっても、既存荷主の許容遅延を超えればREJECT | 新規受注のために既存顧客の条件を破っていないか |
| JD32 参加可能でも赤字 | 参加・引渡しはPASSでも、追加貢献利益はマイナス | 実際に利益が残る料金・原価条件か |

「費用・初期投資・工数の仮定も変更する」を開くと、既存の入力項目を編集できます。追加輸送・荷役・調整・システム・補償・機会損失を差し引いた単便利益、初期費用の単純回収運行数、調整工数の仮定を比較します。不明な費用は空欄のままにし、採算未確定として扱います。工数の仮定を利益へ重ねて加算しません。表示金額はサービスの見積価格ではありません。採算入力は試算用であり、各社の契約金額・承認対象そのものを変更するものではありません。

**黒字試算は参加許可ではありません。参加・引渡し条件が未成立の案について、画面は投資回収の成立を示しません。** 初期費用の回収運行数は、条件成立後に同額の利益が毎回続くという単純計算であり、需要・稼働頻度・税金・資金繰り等を含む投資評価ではありません。

## 次の共同実証で確かめること

最初は既存1ルート、運送会社1社、既存荷主2社＋追加候補1社。現行業務を変更せず、過去の運行記録と例外ケースを使った机上比較から始める設計を想定しています。

確認するのは、**追加荷主の受入れ条件、運送会社の増分採算、初期設定・再承認まで含む参加調整の負担**です。通常の手順と同じ案件・同じ条件で比較し、候補企業の参加意向や料金・原価を確認したうえで商用化を判断します。実データは公開リポジトリと分けて管理します。

その後、別の荷主・ルートで同じ方式を適用できるかを検討します。後続の実証・展開は提案であり、この固定1ルートPoCの実証済み成果ではありません。先行参加企業の事業条件・利用条件は個別協議とし、本公開により優先権や収益分配を約束するものではありません。

## まず動かす

### ブラウザ

ZIPを展開し、同じフォルダの **`index.html`** をブラウザで開きます。APIキー、Python、サーバー、外部通信は不要です。GitHub Pagesへ配置する場合も、このファイルが入口になります。

重量を600kgから800kgに変更すると、計画版が上がって再確認待ちになります。「合成承認・計画根拠を更新」だけでは旧版の引渡し確認を使えません。「合成引渡し確認を更新」まで行うと、条件が成立する案では再びPASSになります。容量超過等を残したまま承認ボタンを押しても、その違反は消えません。

### Python

Python 3.10以降を想定した標準ライブラリだけの実装です。Python 3.12を使用する場合も追加パッケージは不要です。フォルダ内で次を実行します。

```console

```

WindowsでPython Launcherを利用する場合は`python`を`py`に置き換えます。実行ファイル・ケース定義はスクリプトのあるフォルダを基準に読み込みます。

## 何を検証するか

| 判定 | 検証する条件 |
|---|---|
| R01 対象・版と既存貨物 | 固定ルート・条件版の一致、A・B社の既存貨物量の維持 |
| R02 容量・混載 | 出発時重量4,000kg以下、パレット10枚以下、各荷主の混載確認 |
| R03 納品条件 | 各社の時間帯、既存荷主の遅延上限、A→追加荷主→Bの時刻順 |
| R04 費用・役割の合意 | 所定の条件版、運送会社と3荷主の費用合意、確認担当の一致 |
| R05 情報開示の範囲 | 所定の共有先と許可した要約項目だけを要求しているか |
| R06 共同承認 | 必須4主体の承認、重複・別名義・撤回・版違い・内容違い・期限 |
| R07 計画根拠の有効性 | 容量・予定時刻の確認、対象計画との対応、有効期間 |
| R08 データ区分・利用範囲 | 合成データ区分と模擬操作の範囲 |

集約順は **REJECT ＞ HOLD ＞ PASS** です。既知の不適合があればREJECT、不適合がなく未確認だけならHOLD、8条件がすべて成立すればPASSです。全件を保留して安全に見せる設計ではなく、条件がそろったケースはPASSになります。

未確認値は`null`。0、false、未確認を混同しません。既知の荷量だけで上限を超える場合は、ほかに未確認値があってもREJECTです。承認・根拠の有効期間は開始時刻を含み終了時刻を含みません。納品時間帯・容量上限は境界を含みます。時刻は架空の1日の0時からの分数であり、現実の時計・タイムスタンプ認証ではありません。

不正な入力形式は入力エラーです。未知の項目、重複JSONキー、非整数、NaN、真偽値を重量として指定する入力、重複した開示項目、存在しない荷主等をPASS/HOLDへ読み替えません。

### 参加・引渡し・採算を混同しない

**参加判定**は、定義した共同配送案を採用する条件の成立です。全運行の安全性や配送完了を意味しません。

**引渡し判定**は、参加条件に加え、今回の追加荷主への送り手・受け手、数量・荷姿確認、双方の確認、計画との対応、有効期間を検査します。参加PASSでも受領確認がなければ引渡しHOLDです。担当役割の照合であり、事故の法的責任を自動的に決めるものではありません。

**採算**は別計算です。合成の追加売上から、追加輸送費、荷役費、調整・管理費、システム費、既存荷主への補償、他案件の機会損失を引きます。単便の追加貢献利益をPOSITIVE、NEGATIVE、BREAKEVEN、UNKNOWNに分類し、未知の原価を0にしません。初期費用は単便利益に混ぜず、正の利益があるときだけ単純な回収運行数を算出します。

正常例の8,000円は、20,000円−5,000円−3,000円−3,000円−1,000円という架空の計算です。受注・収益・投資回収を実証した値ではありません。人手30分・利用時10分・初期設定120分という工数も仮定であり、実測ではありません。時間削減を利益に重ねて自動加算しません。利益が負でも参加判定自体は変えず、料金・原価の見直しが必要なことを別表示します。

## 記録の保存・再検証

「検証記録JSONを保存」で、現在の入力、適用した公開条件の識別値、判定、理由、採算を1つの記録に保存できます。Pythonの出力をブラウザに読み込み、ブラウザの出力をPythonで再検証できます。

```console
# 1ケースだけ保存
python poc.py run --case JD02 --out output/hold.json

# ブラウザで保存した記録も同じコマンドで再検証
python poc.py verify output/hold.json

# 合成ケースを完全な入力JSONに展開
python poc.py export-input JD01 --out output/input.json

# 公開モデル内の入力を評価。承認や不足値の自動補完はしない
python poc.py evaluate output/input.json --out output/record.json
```

再検証では、入力の形式、固定した公開条件、内容ハッシュ、入力から再計算した8条件・理由・引渡し・採算を照合します。標準38ケースの一式では、入力の差替え・順序変更・欠落・集計変更も検査します。**正しく記録されたHOLDやREJECTは再検証に成功しますが、PASSに変わるわけではありません。**

SHA-256は内容の識別・整合性確認に使います。電子署名、発行者認証、時刻認証ではありません。入力からすべて整合的に作り直した別の記録を、外部の認証情報なしに偽造と識別することはできません。過去時点の記録が再検証できても、現在の利用許可にはなりません。

標準ケースの正解ラベル`expected`はテストとの比較だけに使用し、判定計算には使いません。判定器は通常の評価・再検証中に承認データを作成しません。合成承認の作成はケース初期化か明示的な模擬操作だけです。

### 模擬操作と再使用停止

両判定がPASSの記録にだけ模擬許可を作ります。使用時は、元記録・許可の対応、現在の計画、時計の逆戻り、現在の参加・引渡し条件をもう一度検査します。失敗時は操作を返さず、使用状態も変更しません。

同じルート・計画ID・版・引渡し先に対する模擬操作は、保持した使用状態では二度目を停止します。採算だけを書き換えて記録を作り直しても、この使用識別値は変わりません。画面の使用状態はメモリ内にあり、再読込・ケース切替でリセットします。状態の永続化、複数端末間の排他、改変耐性、実装を迂回した実運行の防止は本PoCに含みません。

### 共有用要約と完全な記録

「共有用要約JSON」は、許可された計画識別情報と判定だけを取り出したものです。重量、採算、承認の詳細、元データを含めません。開示条件が不適合の場合は出力を止めます。

これは固定項目の選別です。情報の秘匿性、匿名性、複数の結果からの推測防止まで保証するものではありません。要約単体では完全な再検証はできません。**完全な検証記録には合成の入力・採算を含むため、実企業データをそのまま公開する形式ではありません。**

## ケースを変更するとき

`cases.json`の`base`は承認・確認データを作る前の合成基礎入力、`scenarios`はその変更点です。`refresh`はケース準備段階の合成確認の作成を指定します。`none`は旧承認を維持、`all`は改訂計画に対する合成確認を明示的に作り直します。実在人物の承認ではありません。

画面は単独で動くよう同じデータを内包しています。ケースの変更後は次を実行し、データの一致と期待結果を確認します。

```console
python poc.py sync
python poc.py ci
```

`profile`はPython・ブラウザ・Leanで同じ参照値に固定しています。変更を自動的に正当化する更新コマンドはありません。会社の条件や許可項目そのものの変更は、単なるケース追加とは区別して仕様・実装・証明モデルをレビューする対象です。C社からD社への切替は固定した2候補の例であり、任意の会社・システムへの汎用的な接続や線形コストを実証するものではありません。
